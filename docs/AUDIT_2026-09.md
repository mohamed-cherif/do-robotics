# Pre-release audit — September 2026

Branch `audit/pre-release`, based on the baseline snapshot `07b07ac` on
`main` (the folder was not a git repository before the audit). Every change
is a separate commit with the reasoning in its message.

## 1. Executive summary

**Health before the audit:** a capable, well-structured app with a real
Python interpreter, a clean protocol and good unit tests for pure logic —
but with **defects that would have made the headline features fail on
real devices**:

- object detection returned the wrong labels (people were never detected,
  everything else was labelled "person") because the model's class and
  score outputs were swapped;
- Bluetooth could not work on Android 7–11 (missing permissions);
- stopping a program while the camera or microphone was starting left them
  on for the rest of the session; a late-finishing Python run could leave
  motors driving with the UI showing "stopped";
- a screen timeout left the robot steering toward a frozen camera frame;
- in the block editor, editing the second block of a chain silently changed
  the first, and fresh blocks ran different values than they displayed;
- the RoboPython interpreter hung on modest recursion, rejected any
  bracket split over lines, and could freeze the app with one line.

**Health after:** all of the above are fixed and covered by tests where a
test is possible; `flutter analyze` is clean; **the test suite grew from
48 to 140+ tests**; release APKs build (arm64 35.5 → 28.9 MB); the detector
was measured on COCO for the first time; docs, CI and contributor files are
in place.

**Go / no-go for open-sourcing: GO after the owner decisions below, with
one condition** — do not publish an installable release until the device
checklist has been run at least once on a real Android 10/11 phone and a
recent one with a real robot. The code is ready to be public; the
hardware-facing behaviour is not yet verified on hardware.

**Blockers before making the repository public**

1. Choose a license and add `LICENSE` (+ `NOTICE` for the model). *(decision)*
2. Decide what to do with the CAD/STL files and `eye_animation.ino`
   (third-party provenance) — they are kept out of git for now. *(decision)*
3. Fill the contact placeholders in `SECURITY.md` and `CODE_OF_CONDUCT.md`.

**Blockers before the first public release (APK/store)**

4. Run `docs/DEVICE_TEST_CHECKLIST.md` on hardware.
5. Choose the final `applicationId` (it is `com.example.do_robotics`).
6. Firmware: ESP32 pin whitelist and the stale-TCP-client fix (§3, F1–F2).

## 5. Verification report

**Ran here (Windows 11, Flutter 3.38.5):**

- `flutter analyze` — no issues; `flutter test` — all tests pass (140+),
  including regression tests that fail on the baseline (checked for the
  runner double-run/freeze and the block-editor chain edit by running the
  new tests against the baseline worktree).
- Release builds (`--split-per-abi`) of the baseline and of the branch;
  merged release manifests inspected for permissions.
- TFLite inference of both bundled models on COCO images (output roles,
  accuracy, latency) with TensorFlow 2.21.
- Widget tests of the block editor, Python tab and six other pages at
  360 × 740 dp.

**Reasoned about but not executed:**

- Everything involving the camera, microphone, speech engine, Bluetooth,
  USB, WiFi/mDNS, sensors, lifecycle (background/screen-off), and all
  firmware behaviour. The fixes are small, targeted and covered by the
  device checklist, but **they are unverified on hardware**.
- The iOS Swift code and plist changes (no Mac available).
- Firmware findings (not compiled; no changes made).

## 8. Roadmap — first three months after release

**Month 1 — stabilize on hardware**
- Run the device checklist on 3 phones × ESP32/Uno; fix what it finds.
- Firmware F1–F4 (pin whitelist, TCP client handling, AVR servo pool,
  pin 13), then F8/F9 (per-device names/passwords, credential erase).
- Decisions D5/D6 (portrait lock + mount setting, robot-frame offsets).
- Publish a signed APK on GitHub Releases; turn on Dependabot and GitHub
  private vulnerability reporting.

**Month 2 — learning experience**
- Variables (set/change/read) in blocks and code generation.
- Accessibility pass (A3): labels, 48 dp targets, tap-to-attach editing.
- Share programs (export/import JSON, QR code).
- Live telemetry panel in the Blocks tab (sensor values, target crosshair).
- Collect phone benchmarks (inference ms, battery/10 min) from volunteers;
  tune the Performance default (D9).

**Month 3 — capability**
- Sensor feedback from the board (distance sensor, bumpers, battery
  voltage) via reverse control frames.
- Gyro-assisted motion blocks ("turn 90°", "drive straight").
- Bonjour/NSD discovery (A5) and TTS/recognizer audio focus (A4).
- Start the iOS port if there is demand (APPLE_FEASIBILITY plan).
- Optional: EfficientDet-Lite1 as an "accurate" model on capable phones,
  validated with `tools/model_eval`.
